# 의도 분류·Rule 엔진 상호작용과 필요 데이터셋

이 문서는 두 가지를 설명한다. 첫째, 사용자 문의의 의도(문의유형)가 어떻게 분류되고 그
결과가 Rule 엔진과 어떻게 맞물려 담당부서·우선순위를 결정하는지. 둘째, 이 구조가 실제로
동작하려면 문의유형별로 어떤 데이터셋이, 왜 필요한지.

## 1. 의도 분류와 Rule 엔진의 상호작용

### 1-1. 역할 분담

| 단계 | 담당 | 결정하는 것 |
|---|---|---|
| `classify_node` | LLM (`LLMClassification` 스키마) | 문의유형, 핵심요청, 감정상태, 분류근거 |
| `rules_node` | `rules.yaml` (키워드 매칭) | 담당부서, 우선순위, 관리자검토 필요 여부 |

담당부서와 우선순위는 **LLM이 판단하지 않는다.** `classify_node`가 쓰는 `LLMClassification`
스키마 자체에 이 두 필드가 없어서, LLM은 애초에 이 값을 낼 수 없다. 같은 문의가 매번
같은 부서·우선순위로 배정돼야 하는데, LLM에게 맡기면 호출마다 결과가 흔들릴 수 있기
때문이다. 이 두 값은 전적으로 `rules_node`가 `rules.yaml`만 보고 결정한다.

### 1-2. 상호작용 흐름

```
사용자 입력(raw_text)
      │
      ▼
[classify_node] ── LLM 호출 ──▶ 문의유형 하나 확정
      │                         (신청/등록, 변경/정정, 취소/환불,
      │                          오류/장애, 불만/신고, 안내/조회, 일반문의)
      ▼
[rules_node]
  ① 담당부서 규칙 순회
     - 규칙마다 applies_to(적용 대상 문의유형) 확인 → 문의유형이 안 맞으면 후보 제외
     - 남은 규칙 중 raw_text 키워드가 매칭되는 것만 후보로 수집
     - 후보가 여러 개면 규칙별 priority 숫자가 가장 높은 것이 최종 담당부서
     - 문의유형별 fallback 규칙(priority: -1)이 있어 후보가 하나도 없어도 값이 비지 않음
  ② 우선순위 규칙 순회
     - applies_to 없이 모든 문의유형에 항상 적용
     - 매칭된 값들 중 등급(낮음<보통<높음<최상)이 가장 높은 것이 최종 우선순위
     - 관리자검토필요를 세팅하는 규칙(민감민원, 법적조치_경고, 긴급도_최상)이 있으면
       requires_manager_review = True
      ▼
requires_manager_review?
  ├─ True  → RAG/답변생성 건너뛰고 관리자 검토 안내문 생성 → END
  └─ False → RAG 근거 검색(retrieve) → 답변 초안 생성(generate) → END
```

### 1-3. 왜 이렇게 나눴는가

- **일관성**: 담당부서·우선순위처럼 "같은 입력엔 항상 같은 결과"가 요구되는 판단을 결정론적
  규칙으로 고정했다. LLM 판단은 자연어 이해가 필요한 문의유형 분류에만 맡긴다.
- **설명 가능성**: `rule_flags`(matched_rules, candidate_departments, review_reasons)에
  어떤 규칙이 왜 매칭됐는지 그대로 남아, "왜 이 부서로 갔는지"를 사후에 재구성할 수 있다.
- **안전망**: 문의유형별 fallback 규칙 덕분에, 아무 구체적 규칙도 안 걸린 경우에도 담당부서·
  우선순위가 항상 정해진다.

## 2. 문의유형별로 필요한 데이터셋과 그 이유

담당부서·우선순위는 Rule로 결정되지만, **답변 초안의 품질은 RAG가 얼마나 관련 있는 근거
문서를 찾아주느냐에 달려 있다.** 문의유형마다 실제로 검색될 만한 근거 데이터가 없으면,
LLM은 근거 없이 일반 지식으로 답변을 지어내게 된다(실제로 겪었던 문제). 따라서 문의유형별로
아래와 같은 데이터셋이 필요하다.

| 문의유형 | 필요한 데이터 성격 | 데이터가 필요한 이유 |
|---|---|---|
| 신청/등록 | 신청 절차, 필요 서류, 접수 방법 안내 | "~신청하려면 뭐가 필요한가요" 류 질문에 절차·서류 목록 같은 사실 정보가 필요하고, 이는 LLM이 지어내면 안 되는 영역이다 |
| 변경/정정 | 정보 변경 절차, 정정 가능 범위·조건 | 무엇을, 언제까지, 어떤 조건에서 변경할 수 있는지는 서비스마다 다른 정책이라 근거 문서 없이는 정확한 답변이 불가능하다. `coupang_faq_personal_info`(40건, 가입/탈퇴·개인정보 설정·인증·비밀번호 관리)로 채워짐 |
| 취소/환불 | 환불 정책, 결제수단별 환불 소요기간 | 환불 기준·기간은 자주 바뀌고 세부 조건이 많아, 근거 문서 대조 없이 답하면 실제 정책과 어긋날 위험이 크다 |
| 오류/장애 | 시스템 오류 대응 절차, 장애 공지 이력 | "언제까지 기다려야 하나요", "누구에게 연락해야 하나요" 같은 질문은 실제 대응 매뉴얼에 있는 구체적 기준(예: 지연 허용 시간)이 있어야 정확히 답할 수 있다 |
| 불만/신고 | (RAG 근거보다 인적 대응이 우선) | 민감 민원은 Rule에서 이미 관리자 검토로 즉시 분기되어 RAG/답변생성을 건너뛴다. 근거 문서보다 담당자의 직접 대응이 필요한 영역이라 데이터 우선순위가 낮다 |
| 안내/조회 | 이용방법, 정책 안내 FAQ | 단순 정보 요청이라도 오답을 주면 신뢰가 깨지므로, 실제 FAQ 대조가 필요하다 |
| 일반문의 | 포괄적 FAQ | 특정 카테고리에 안 걸리는 문의를 위한 최소한의 대비책으로 필요하다 |

### 공통 원칙: 왜 "그럴듯한 일반 지식 답변"이 아니라 실제 데이터가 필요한가

이 시스템은 담당자가 검토 후 발송하는 **답변 초안**을 만드는 시스템이다. 실제 정책과 다른
내용을 그럴듯하게 지어내면, 검토 과정에서 오류를 걸러내지 못했을 때 잘못된 답변이 그대로
나갈 위험이 있다. `generate_node`가 "근거 문서에 없는 내용은 지어내지 말라"고 LLM에
지시하고 있지만, 애초에 검색할 근거 자체가 없으면 이 지시는 지켜질 수 없다. 그래서 문의유형별로
실제 데이터가 갖춰져 있어야 하며, 데이터가 아직 없는 유형은 "근거 없음"을 있는 그대로
인정하고(빈 근거 → 담당자 확인 필요 안내) 지어낸 답을 내보내지 않는 것이 원칙이다.

## 3. 담당부서 기준 데이터 매핑 (`rules.yaml`의 `data_source`)

문의유형은 담당부서와 항상 1:1이 아니다. 예를 들어 `배송_물류_분류`는 `applies_to:
["취소/환불", "안내/조회"]` 두 문의유형에 걸쳐 있지만 항상 물류팀으로, `법무_분류`도
`["취소/환불", "불만/신고"]` 두 문의유형에 걸쳐 있지만 항상 법무팀으로 귀결된다. 즉
**담당부서가 "실제로 누구의 지식이 필요한가"를 문의유형보다 더 정확하게 집약**한다. 그래서
`rules.yaml`의 담당부서 규칙마다 `data_source` 필드로 참고해야 할 데이터를 직접 명시했다
(현재는 문서화 목적이며, `retrieve_node`가 이 값 기준으로 검색을 필터링하도록 확장하는 건
후속 작업이다).

| 담당부서 | data_source | 비고 |
|---|---|---|
| 정산팀 | `coupang_faq` | 환불/취소/반품 FAQ 65건 — 충분 |
| 회원관리팀 | `duty_free_faq`(개인정보 8건) + `coupang_faq_personal_info`(40건) | 가입/탈퇴·개인정보 설정·인증·비밀번호 관리·로그인 — "변경/정정" 공백을 메움 |
| 고객센터 | `chroma_merged_faq` | duty_free_faq 이용방법·개인정보·결제문의 등 + coupang_faq 이용정책 + coupang_faq_order_payment(주문/결제 156건) |
| IT지원팀 | `it_support_faq` | 생성된 IT지원 FAQ 88건(로그인/접속불가/오류/서버/먹통/안 열림) — 공백 메움 |
| 물류팀 | `coupang_faq_delivery` | 배송 전용 FAQ 82건(자주묻는질문_배송문의 ep_1~ep_8) — 공백 메움 |
| 행정팀 | `admin_team_faq` | 생성된 행정팀 FAQ 126건(신청/등록/발급/서류/접수) — 공백 메움 |
| 마케팅팀 | `marketing_promotion_faq` | 생성된 마케팅/프로모션 FAQ 88건(이벤트/쿠폰/할인/프로모션/광고) — 공백 메움 |
| 법무팀 | `legal_team_faq` | 생성된 법무팀 FAQ 105건(소송/고발/약관/법적조치/손해배상 절차) — 공백 메움. 단 관리자검토필요가 안 걸려 있어 안전관리팀과 달리 실제로 retrieve_node/generate_node에서 쓰임 |
| 안전관리팀 | 없음 (의도적) | RAG 근거보다 즉시 에스컬레이션이 우선. `safety_team_faq`(167건, 안전수칙/응급처치 + 신고·조사·보상 절차)를 Supabase/Chroma에 적재는 해뒀지만, `안전_사고_분류` 규칙이 `관리자검토필요: true`라 retrieve_node를 안 타므로 이 경로에서는 미사용 |
| 고객지원총괄팀 | `sensitive_complaint_faq`(민감민원 규칙에는 없음) | `민감민원`(관리자검토필요: true)은 RAG 자체를 건너뛰어 데이터 불필요. 다만 같은 담당부서라도 `기본_불만신고` fallback은 관리자검토필요가 없어 실제로 retrieve_node를 타므로, 생성된 FAQ 105건(불만/신고 절차·SLA 안내)을 이 규칙에만 채움 |

"없음(의도적)"으로 표시한 안전관리팀·고객지원총괄팀은 데이터가 없어서가 아니라, 설계상
RAG/LLM 답변 생성을 건너뛰고 사람이 바로 처리해야 하는 경로(관리자검토필요: true)라
데이터가 필요 없다. 법무팀은 같은 "즉시 에스컬레이션" 취지로 설계됐지만 실제로는
관리자검토필요가 걸려 있지 않아 RAG 근거(`legal_team_faq`)가 채워졌다 — 이 규칙에도
관리자검토필요를 걸지는 별도 결정 사항으로 남겨뒀다. 나머지 부서는 모두 근거 데이터가
채워졌다.
