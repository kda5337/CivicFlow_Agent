# 2026-07-23 작업 기록

## 요약

문의유형 분류 스키마를 기존 6개(프롬프트는 8개로 불일치하던 버그 포함)에서, 실제 프롬프트와 일치하는 도메인 무관 7개(신청/등록, 변경/정정, 취소/환불, 오류/장애, 불만/신고, 안내/조회, 일반문의)로 재정의했다. `rules.yaml`을 문의유형별 담당부서 규칙 9개와 우선순위 규칙 7개로 재구성하고, 여러 규칙이 동시에 매칭될 때 승자를 가리는 `priority` 필드와 특정 문의유형에만 적용되는 `applies_to` 필드를 새로 도입했다. `classify_node`가 담당부서와 우선순위를 더 이상 판단하지 않도록 LLM 출력 스키마를 `LLMClassification`으로 분리하고, 이 두 필드는 오직 `rules.yaml` 규칙으로만 결정되도록 `rules_node`를 수정했다. 문의유형 7개 각각에 키워드 없이 항상 매칭되는 기본값(fallback) 규칙과 우선순위 기본값 규칙을 추가해, 구체적인 규칙이 하나도 안 걸려도 담당부서/우선순위가 항상 채워지도록 만들었다. 겹치는 담당부서 후보를 `candidate_departments`로 별도 보존하도록 `rules_node`와 `db/schema.sql`을 수정했고, 값이 같은 중복 후보는 제거하도록 다시 고쳤다. 문의유형 이름이 바뀌면서 죽은 코드가 된 `build.py`의 `curriculum_lookup` 라우팅을 삭제하고, `retrieve.py`의 merged_faq 라우팅 규칙 이름도 새 이름(`결제_정산_분류`)으로 맞췄다. `intake_node`의 `RELEVANCE_PROMPT`가 옛 도메인 예시만 담고 있어 응급·사고 신고가 관련없음으로 잘못 거부되는 버그를 발견해 새 7개 카테고리 기준으로 다시 썼다. 이 모든 변경을 검증하기 위해 `backend/test_intent_classification.py`를 새로 만들어 7개 문의유형과 관련없음 케이스를 실제로 실행하며 확인했다.

## 문의유형 분류 스키마 재정의

- `backend/app/models/schemas.py`: `ClassificationResult.문의유형` Literal을 6개(신청/변경/취소환불/오류장애/일반문의/긴급문의)에서 7개(신청/등록, 변경/정정, 취소/환불, 오류/장애, 불만/신고, 안내/조회, 일반문의)로 교체.
- `backend/app/graph/prompts.py`: `CLASSIFY_PROMPT`가 8개 유형(졸업요건/교육과정_문의 포함)을 언급하는데 실제 스키마 Literal은 6개뿐이던 기존 불일치 버그를 새 7개로 완전히 일치시켜 해결.
- `우선순위` Literal에 `최상` 단계를 추가해 낮음/보통/높음/최상 4단계로 확장(응급·사고성 문의를 별도로 구분하기 위함).

## `rules.yaml` 재구성: 담당부서/우선순위 규칙 세분화

- 담당부서 규칙 9개(IT장애_분류, 결제_정산_분류, 배송_물류_분류, 신청_행정_분류, 계정_회원_분류, 법무_분류, 안전_사고_분류, 마케팅_프로모션_분류, 민감민원)를 문의유형별로 새로 정의.
- 각 규칙에 `applies_to`(적용 대상 문의유형 목록)를 추가해, classify가 정한 문의유형과 무관한 규칙 후보는 애초에 검사 대상에서 제외되도록 함.
- 담당부서 규칙에 `priority`(정수) 필드를 추가해, 여러 규칙이 동시에 매칭돼도 순서(yaml 작성 순서)가 아니라 명시적 숫자로 결정론적으로 승자를 가리게 함.
- 우선순위 규칙 7개(긴급도_최상, 긴급도_높음, 반복문의_가중, 법적조치_경고, VIP고객_가중, 단순조회_낮음, 정기문의_낮음)는 `applies_to` 없이 모든 문의유형에 횡단 적용.

## `classify_node`에서 담당부서/우선순위 판단 제거

- `backend/app/models/schemas.py`: LLM이 실제로 판단하는 필드(문의유형/핵심요청/감정상태/분류근거)만 담은 `LLMClassification`을 신설하고, 담당부서/우선순위를 포함한 최종 결과용 `ClassificationResult`는 별도로 유지.
- `backend/app/graph/nodes/classify.py`: `get_structured_llm(LLMClassification)`으로 교체해 LLM이 담당부서/우선순위를 아예 출력할 수 없는 구조로 변경.
- `backend/app/graph/prompts.py`: `CLASSIFY_PROMPT`에서 우선순위/담당부서 판단 지시를 제거하고 "이후 Rule 엔진이 결정하므로 판단하지 마세요"를 명시.

## 문의유형별 기본값(fallback) 규칙 추가

- `rules.yaml`에 문의유형 7개 각각에 대응하는 기본값 규칙(기본_신청등록, 기본_변경정정, 기본_취소환불, 기본_오류장애, 기본_불만신고, 기본_안내조회, 기본_일반문의)을 추가. `priority: -1`, `keywords` 없음으로 항상 매칭되되 구체적 규칙보다 항상 밀리게 함.
- 우선순위 기본값 규칙(기본_우선순위, 결과값 `보통`)도 `priority: -1`로 추가.
- `backend/app/graph/nodes/rules.py`: `keywords`가 비어있으면 항상 매칭으로 간주하도록 수정하고, 우선순위 후보의 랭킹을 규칙별 `priority`(있으면 이 값)와 값 자체의 등급(`_PRIORITY_RANK`, 없으면 이 값)으로 이원화해, "단순조회_낮음" 같은 하향 규칙이 fallback의 `보통`보다 밀리지 않도록 함.

## `candidate_departments` 추적 및 중복 제거

- `backend/app/graph/nodes/rules.py`: 매칭된 담당부서 후보 전체를 `rule_flags.candidate_departments`로 보존해, 왜 이 부서로 결정됐는지 나중에 추적 가능하게 함.
- `db/schema.sql`: `inquiries` 테이블에 `candidate_departments TEXT[]` 컬럼 추가.
- 서로 다른 규칙이 같은 부서 값을 가리켜 리스트에 중복이 남던 문제를 발견해, 값 기준으로 중복 제거하도록 수정(`list(dict.fromkeys(...))`).

## `build.py`/`retrieve.py` 라우팅 정리

- `backend/app/graph/build.py`: 문의유형 재설계로 인해 더 이상 매칭될 수 없게 된 `curriculum_lookup` 노드/라우팅(`_CURRICULUM_RULES`, 관련 엣지)을 전부 삭제. `curriculum_lookup.py` 노드 파일 자체는 `backend/scratch_test_nodes.py`가 별도로 직접 참조하고 있어 그대로 유지.
- `backend/app/graph/nodes/retrieve.py`: `_MERGED_FAQ_RULES`가 참조하던 옛 규칙 이름(`취소환불_분류`)을 새 이름(`결제_정산_분류`)으로 수정. `rules.yaml`의 `결제_정산_분류` 키워드에 빠져 있던 "반품"도 추가해 취소/환불/반품 문의가 모두 `chroma_merged_faq`로 라우팅되게 함.

## `RELEVANCE_PROMPT` 버그 수정

- `backend/app/graph/prompts.py`의 `RELEVANCE_PROMPT`가 옛 도메인 예시("졸업요건/교육과정 안내" 등)만 나열하고 있어, 새로 추가한 `불만/신고`(안전사고 포함) 카테고리에 해당하는 입력("지금 사고가 나서 응급으로 도움이 필요합니다!")이 관련없음으로 잘못 거부되는 것을 테스트로 발견.
- 새 7개 문의유형 기준으로 프롬프트를 다시 써서, 사고·피해·응급 상황 신고도 이 시스템이 처리하는 민원·문의에 포함됨을 명시.

## 검증: `backend/test_intent_classification.py`

- intake → classify → apply_rules 파이프라인을 문의유형 7개 대표 샘플과 관련없음 케이스로 직접 실행해, classify의 1차 판단과 rules 적용 후 최종 담당부서/우선순위/`matched_rules`/`candidate_departments`/`requires_manager_review`를 나란히 출력하는 스크립트를 `backend/` 바로 아래에 작성.
