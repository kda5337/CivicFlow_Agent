# 2026-07-28 작업 기록

## 요약

프론트엔드(`npm run dev`, Vite)를 실행해 문의 접수 화면을 테스트하던 중 5173 포트가 이미 사용 중이라 5174로 뜨면서 "Failed to fetch"가 발생, `backend/app/main.py`의 CORS `allow_origins`에 `http://localhost:5174`가 없던 게 원인임을 확인해 추가하고 백엔드를 재시작해 해결했다. 이 과정에서 문의 1건당 응답이 7~25초 걸린다는 문제가 드러났는데, 원인은 `intake→classify→apply_rules→retrieve→generate`가 전부 직렬로 실행되면서 LLM 호출 3회 + 매 요청 새로 여는 Supabase 커넥션이 반복되기 때문이었다. 이를 해결하기 위해 문의 임베딩 유사도 캐시(`query_cache`, Chroma 컬렉션)를 새로 설계·구현했다: `app/rag/query_cache.py`에 저장(`store_cache_entry`)/조회(`lookup_cache_entry`) 함수를, `app/graph/nodes/cache.py`에 그래프 노드(`check_cache_node`/`store_cache_node`)를 추가하고, `build.py`의 `StateGraph` 맨 앞에 `check_cache`를 붙여 캐시 HIT면 `intake~generate`를 전부 건너뛰고 즉시 반환하도록, MISS면 기존 파이프라인을 그대로 타되 `generate` 이후 결과를 캐시에 저장하도록 배선했다(관리자검토필요였던 결과는 저장하지 않음). 유사도 임계값은 실제 데이터로 계측해 0.80으로 정했다(진짜 재질문 0.79~0.87 vs 같은 부서의 다른 이슈 0.60 vs 무관한 질문 0.30). 캐시를 채우기 위해 `backend/seed_query_cache.py`(run/commit 분리 스크립트)를 만들어 IT지원팀·정산팀·물류팀·행정팀·회원관리팀 5개 부서, 부서당 10건(실제 FAQ 8건 + 재질문 2건) 총 50건을 실제 파이프라인에 통과시켜 사용자 확인을 받은 뒤 하나씩 커밋했다. 이 과정에서 LLM 분류(`classify_node`)가 의도한 부서로 항상 떨어지지 않는다는 걸 반복적으로 확인해(정산팀 2건, 물류팀 2건+재시도 1건, 행정팀 4건, 회원관리팀 5건+재시도 3건 교체) 질문 문구를 "~해주세요/~하고 싶어요" 같은 직접 행동 요청 톤으로 바꿔가며 재시도했다. 최종적으로 캐시를 그래프에 연결한 뒤 실측한 결과, 캐시 MISS는 기존과 동일하게 7~17초가 걸리지만 캐시 HIT는 서버가 웜 상태일 때 0.35초로 확인됐다. 마케팅팀·법무팀 시딩은 아직 진행 전이라 `query_cache`는 현재 50건만 있다.

## 프론트엔드 CORS 오류 수정

- 증상: 프론트엔드(`http://localhost:5174`, 5173이 이미 사용 중이라 밀려서 뜬 포트)에서 문의 등록 시 "요청 실패: Failed to fetch".
- 원인: `backend/app/main.py`의 `CORSMiddleware`가 `allow_origins=["http://localhost:5173", "http://localhost:3000"]`만 허용하고 있어 5174 origin이 브라우저에서 차단됨.
- 조치: `allow_origins`에 `"http://localhost:5174"` 추가. 백엔드가 `--reload` 없이 떠 있어 코드 변경이 반영되지 않아 프로세스를 재시작(`taskkill` 후 `uvicorn app.main:app --port 8000` 재기동).

## query_cache 설계 및 구현

- 문의당 7~25초가 걸리는 원인이 `intake`/`classify`/`generate` 3회의 순차 LLM 호출 + `retrieve_node`가 매번 새로 여는 `psycopg2.connect`(Supabase)임을 확인.
- `backend/app/rag/query_cache.py` 신규 작성:
  - `store_cache_entry(inquiry_id, raw_text, state)`: 파이프라인 최종 결과(`classification`/`rule_flags`/`retrieved_docs`/`draft_answer`)를 Chroma `query_cache` 컬렉션에 저장. `rule_flags.requires_manager_review=true`인 결과는 저장하지 않음(안전/법적 사안은 매번 사람 검토가 필요하므로).
  - `lookup_cache_entry(raw_text)`: `query_cache`에서 코사인 유사도 top-1을 찾아 임계값(`CACHE_SIMILARITY_THRESHOLD=0.80`) 이상이면 캐시된 결과를 반환, 미만/빈 컬렉션이면 `None`.
  - 임계값 0.80은 실제 저장된 50건을 대상으로 계측: 진짜 재질문(paraphrase)은 0.79~0.87, 같은 부서의 다른 이슈는 0.60, 완전 무관한 질문은 0.30으로 나뉘어, 재현율보다 정밀도를 우선해 그 사이값으로 설정.
- `backend/app/graph/nodes/cache.py` 신규 작성: `check_cache_node`(조회, Langfuse `retriever` 타입 span), `store_cache_node`(저장, 부수효과만 수행).
- `backend/app/graph/state.py`: `InquiryState`에 `cache_hit: bool` 필드 추가.
- `backend/app/graph/build.py`: `StateGraph`에 `check_cache`/`store_cache` 노드 추가. `START → check_cache`로 바꾸고, `_route_after_cache`로 HIT는 `END`, MISS는 기존 `intake`로 분기. `generate → store_cache → END`로 변경해 MISS 결과가 자동으로 캐시에 쌓이게 함.

## 시드 데이터 적재 (50건)

`backend/seed_query_cache.py` 작성 — `run(부서)`는 실제 파이프라인을 태워 결과를 JSON으로 저장하고 요약을 출력, `commit(부서)`는 그 JSON을 읽어 `query_cache`에 반영(LLM 재호출 없음). 부서별로 실제 FAQ 8건 + 표현만 다른 재질문 2건씩 만들어 실행 → 사용자 확인 → 저장 순서로 진행.

- **IT지원팀(10건)**: 전부 의도대로 IT지원팀으로 분류. 재질문 2건도 원본과 동일 FAQ를 정확히 재검색(유사도 0.976/0.756)하는 것으로 RAG 검색 자체의 재질문 대응력도 함께 확인.
- **정산팀(10건)**: 최초 실행 시 2건 이탈 — "환불계좌 등록/변경"은 변경/정정→회원관리팀, "환불은 언제쯤 처리되나요?"는 안내/조회→고객센터로 감. "카드대금이 청구되었습니다"(취소/환불 톤 유지) 및 "주문을 취소했는데 환불은 언제쯤 받을 수 있나요?"로 교체 후 10건 전부 정산팀으로 정상화.
- **물류팀(10건)**: 최초 실행 시 2건 이탈("배송지 변경"→회원관리팀, "물건은 언제쯤 도착"→고객센터, 키워드 "배송" 누락) 교체 후 재실행했더니, 이번엔 "상품파손" 문항이 (동일 텍스트임에도) 불만/신고→고객지원총괄팀으로 분류되는 LLM 비결정성이 새로 발견됨 — 사용자 선택에 따라 해당 문항을 "배송조회를 했는데 배송정보가 없다고 나와요"로 교체해 최종 10건 확정.
- **행정팀(10건)**: 4건 이탈("서류가 다른가요"/"절차를 거쳐야"/"가능한가요"/"취소할 수 있나요" 톤이 안내·조회·변경 유형으로 흡수됨) — "전과/교환학생/기숙사/졸업유예 신청은 어떻게 하나요" 식 명확한 신청 행동 문구로 교체해 10건 전부 행정팀으로 정상화.
- **회원관리팀(10건)**: 5건 이탈(가장 큰 이탈률 — "가입"은 신청/등록으로, "~되나요/궁금합니다" 톤은 안내·일반문의로 흡수됨). 1차 교체(설정 방법 톤)에서도 3건이 재이탈해, "~변경하고 싶어요" 1인칭 행동 요청 톤으로 재교체한 뒤에야 10건 전부 회원관리팀으로 정상화.

공통적으로 확인된 점: `rules.yaml`의 담당부서 규칙은 `classify_node`(LLM)가 판단한 `문의유형`에 강하게 의존하는데, "절차/가능 여부/설정 방법"처럼 정보 조회 뉘앙스가 섞인 문구는 의도한 유형이 아닌 안내/조회·일반문의·변경정정 등으로 흡수되기 쉽고, 같은 텍스트도 매번 같은 유형으로 분류된다는 보장이 없다(물류팀 사례).
